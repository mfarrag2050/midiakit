# 14 — سجل مراجعات بيانات العميل (Revision History)

نمط Airtable: كل تعديل على كيان قابل للتحرير يُخزَّن حدثاً منفصلاً،
لا يُستبدل في المكان.

## المشكلة اليوم

`brand_kits.config` (وأمثاله من الجداول) يُستبدل عند كل حفظ. غداً يُسأل:
- من غيّر لون شارة العاجل؟
- متى تغيّر الخط من Almarai إلى Tajawal؟
- من أضاف هذا الشعار الذي أثار الشكوى القانونية؟

اليوم: **لا جواب.** الحقل الحالي يحمل الحالة الراهنة فقط. التغيير
مجهول الفاعل والوقت والمحتوى.

## الكيانات المتتبَّعة

| الكيان | الخطر عند غياب السجل |
|---|---|
| **Brand Kit** (الأخطر) | تغيير خفي يخرّب مخرجات محفوظة، ولا يُعرف من مسؤول |
| المشاريع (Projects) | عنوان عاجل حُرّر بعد النشر — من نسخة يستحق الاعتماد؟ |
| القوالب (Templates) — سواء المستوردة أو المستنسخة عن الجاهزة | تحرير قالب مشترك بين عملاء يقلب مخرجاتهم |
| المستخدمون والأدوار | من رفع الصلاحية إلى `admin`؟ متى؟ |
| الأصول (Assets) | من رفع الخط؟ من أقرّ بحق الاستعمال؟ |
| ترقيات الأصول (`brand.assets.version`) | فرق ملموس في المخرجات — يجب أن يكون فعلاً بشرياً مقصوداً |

## البنية

جدول أحداث مركزي بدل تعديل في المكان:

```sql
CREATE TABLE revisions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id    uuid NOT NULL REFERENCES tenants(id),
  entity_type  text NOT NULL,        -- 'brand_kit' | 'project' | 'template' | 'user' | 'asset'
  entity_id    uuid NOT NULL,
  actor_id     uuid REFERENCES users(id),  -- NULL = آلي (ترحيل، خدمة)
  action       text NOT NULL,        -- 'create' | 'update' | 'delete' | 'restore'
  diff         jsonb,                -- الحقول المتغيّرة فقط — للعرض السريع
  snapshot     jsonb,                -- الحالة الكاملة — للاستعادة
  created_at   timestamptz NOT NULL DEFAULT now(),

  UNIQUE (entity_type, entity_id, created_at)
);

CREATE INDEX ON revisions (tenant_id, entity_type, entity_id, created_at DESC);
```

**لماذا حقلَان (`diff` و `snapshot`) لا واحد:**
- `diff` يُقرأ في واجهة السجل ويُعرض للمستخدم في ثانية («غيّر: `colors.text`
  من `#F5F5F5` إلى `#E8E8E8`»).
- `snapshot` يُقرأ عند الاستعادة — لا داعي لتشغيل خوارزمية عكس
  التطبيقات المتتالية على `diff`ات. الاستعادة عملية `INSERT` واحدة.

## الاستعادة إلزامية

سجل يُقرأ ولا يُستعاد منه = **نصف ميزة**. الفريق يرى الخطأ ولا يستطيع
تصحيحه بضغطة، فيستعمل قناة أخرى (نسخ يدوي، دعم).

عملية الاستعادة:
```
1. المستخدم يفتح سجل الكيان X.
2. يختار مراجعة قديمة، يضغط «استعادة».
3. تُقرأ snapshot الخاصة بها.
4. تُنشأ مراجعة جديدة action='restore' بتلك الـsnapshot بحرفها.
5. الحالة الحالية تُحدَّث إلى ذلك المحتوى.
```

**السجل لا يُعدَّل بأثر رجعي.** المراجعة القديمة تبقى في مكانها؛
الاستعادة تُنشئ حدثاً جديداً «restore» يُشير إلى المصدر.

## التكامل مع `brand_snapshot` في `renders`

الجدول `renders` يحمل `brand_snapshot jsonb` — لقطة كاملة من الهوية
وقت التصدير (المرحلة 3). مع سجل المراجعات:

- كل `render` يشير إلى `brand_revision_id` — المراجعة التي كانت الحالة
  الراهنة وقت التصدير.
- التتبّع كامل: من عدّل → متى → أيّ تصدير استخدم أيّ نسخة → متى نشره.
- إن اكتشف العميل خطأً في تصدير قديم، مسار الرجوع واضح.

## سياسة الحجم

بلا حدود، الجدول يتضخّم. **تقدير مبدئي** (ليس قياساً — لا عميل بعد):
لو افترضنا brand_kit بثلاثين حقلاً، ومئة عميل يعدّلون بمعدل خمس مرات
يومياً، فالحجم النظري بضعة ملايين سطر سنوياً معظمها snapshots كاملة.
**الفرضيات كلها بلا سند تجريبي** — العميل الأول لم يبدأ، ومعدل التعديل
الفعلي غير معلوم. يُعاد القياس عند عشرة عملاء نشطين.

**قاعدة الاحتفاظ:**
- لقطة كاملة (`snapshot` مملوءة) كل **عشرة** تعديلات.
- بين اللقطات: `diff` فقط (`snapshot NULL`).
- الاحتفاظ باللقطات القديمة **تسعين يوماً** ثم أرشفة إلى S3.
- الاحتفاظ بالسطور نفسها (بدون snapshot الكامل) **إلى الأبد** — الحجم
  الصغير لا يستحق الحذف.

**الأثر:** الاستعادة إلى تعديل عمره سنة تعمل عبر إحضار أقرب snapshot
قبله من الأرشيف + تطبيق diffات بينه وبين النقطة المطلوبة. عملية أبطأ
(ثانية-ثانيتان) لكن ممكنة.

## عزل المستأجرين (RLS)

**إلزامي.** سجل يسرّب بيانات عميل لآخر **أسوأ** من غيابه — يحوّل
ميزة إلى حادث قانوني.

```sql
ALTER TABLE revisions ENABLE ROW LEVEL SECURITY;

CREATE POLICY revisions_tenant_isolation
  ON revisions
  USING (tenant_id = current_setting('app.current_tenant_id')::uuid);
```

- `app.current_tenant_id` يُعيَّن في كل بداية جلسة/طلب API.
- استعلام بلا هذا الإعداد يفشل — لا استرداد صامت لكل السطور.

## واجهة السجل

- لكل كيان زر «السجل» في الشريط الجانبي.
- قائمة عمودية بمراجعات مرتبة تنازلياً (الأحدث أعلى).
- كل مراجعة تعرض: أيقونة الفاعل + اسمه + توقيت نسبي + عنوان قصير
  للتغيير («غيّر لون العاجل» / «رفع خطاً جديداً» / «رقّى الأصول
  إلى 2026.09»).
- الضغط يفتح جدولاً بحقلين: قبل / بعد.
- زر «استعادة هذه النسخة» أعلى التفاصيل.

## سلوك حذف الكيان

`action='delete'` **لا يحذف السطور** — يُضاف حدث delete جديد. القارئ
الحالي يعرض «الكيان محذوف»، لكن السجل يبقى قابلاً للقراءة والاستعادة
(action='restore' على كيان محذوف يُنشئه مجدداً).

سياسة الحذف الفيزيائي: بعد **سنة** من `delete` بلا استعادة، تُنقل
سطور الكيان كاملةً إلى الأرشيف.

- **L-14:** لا تصمّم trigger لكل جدول على حدة — دالة عامة تأخذ
  `entity_type` كوسيط تتفادى انفجار الكود.
- **L-21:** «حالة النظام» = كل شيء متسلسل زمنياً (revisions) لا مجرد

- **L-27:** لا تنشر ميزة استعادة قبل اختبارها — «سجل يُقرأ ولا يُستعاد
  منه» تصنيف خاطئ يُتخذ من الحدس ولا يُعتمد قبل التنفيذ.
