# 15 — سير العمل التحريري (Editorial Workflow)

**غير سجل المراجعات (`docs/14`):** ذاك يتتبّع بأثر رجعي. هذا **يدير
عملية جارية**.

## المشكلة

الموجود في `docs/09 §التحرير`: بند يتيم بلا تفصيل. الواقع: هذا نظام
كامل.

الفيديو أو البطاقة يمرّون بمراحل، ولكل مرحلة شخص:

```
مسودة → كتابة النص → تحرير الفيديو → مراجعة لغوية → اعتماد → منشور
```

وكل انتقال يحتاج:
- **من ينتقل به** (المسؤول عن المرحلة التالية)
- **متى** (طابع زمني)
- **هل ردّه** (تحوّل عكسي) **ولماذا** (ملاحظة)

بلا هذا، الفريق يدير عمله في Trello أو WhatsApp أو Slack — **وهناك
تنتقل قيمة المنتج**.

## المتطلبات

### 1. حالات قابلة للتخصيص

لا نفرض سير عمل واحد. وكالة قد تحتاج مراجعة لغوية، وكالة أخرى تكتفي
بالاعتماد. تُعرَّف في **إعدادات المستأجر لا في الكود**.

```jsonc
// إعدادات مستأجر:
"workflow": {
  "states": [
    { "id": "draft",       "label": "مسودة",         "initial": true },
    { "id": "writing",     "label": "كتابة النص" },
    { "id": "editing",     "label": "تحرير الفيديو" },
    { "id": "review",      "label": "مراجعة لغوية" },
    { "id": "approval",    "label": "اعتماد" },
    { "id": "published",   "label": "منشور",         "terminal": true }
  ],
  "transitions": [
    { "from": "draft",    "to": "writing",   "roles": ["editor", "approver"] },
    { "from": "writing",  "to": "editing",   "roles": ["writer"] },
    { "from": "editing",  "to": "review",    "roles": ["editor"] },
    { "from": "review",   "to": "approval",  "roles": ["reviewer"] },
    { "from": "review",   "to": "writing",   "roles": ["reviewer"], "label": "ردّ للكاتب" },
    { "from": "approval", "to": "published", "roles": ["approver"] },
    { "from": "approval", "to": "editing",   "roles": ["approver"], "label": "ردّ للمحرّر" }
  ]
}
```

**قوالب سير عمل جاهزة:** ثلاثة نماذج مقترحة في الواجهة عند إنشاء
مستأجر جديد (فردي · فريق صغير · وكالة كاملة)، لكل مستأجر يعدّل عليها.

### 2. أدوار موسَّعة

الأدوار الحالية (`owner | admin | editor | viewer`) لا تكفي للفصل التحريري.
الجديدة:

| الدور | الصلاحية |
|---|---|
| `owner` | كل شيء + الفوترة + حذف المستأجر |
| `admin` | إدارة المستخدمين + ترقية `assets.version` + إعدادات سير العمل |
| `writer` | إنشاء مسودة + كتابة نصّ + إرسال للتحرير |
| `editor` | كل ما سبق + استعمال محرّر الفيديو + إرسال للمراجعة |
| `reviewer` | مراجعة لغوية/تحريرية + الردّ للكاتب |
| `approver` | اعتماد النشر + الردّ للمحرّر |
| `viewer` | قراءة فقط |

- المستخدم يحمل أدواراً متعدّدة (writer + editor مثلاً).
- كل انتقال يفحص `roles` المسموحة له.
- **الفاعل يُخزَّن مع الانتقال** (سجل السير) — راجع docs/14 (revisions).

### 3. الردّ بسبب

المراجع الذي يردّ عملاً يُلزَم بملاحظة. رفض صامت = فريق يعيد
الاكتشاف بنفس الخطأ الأسبوع القادم.

- زر «ردّ» يفتح مربع نصّ إلزامي (لا حفظ بلا نصّ).
- تظهر الملاحظة أعلى الكيان في المرحلة التي رُدّ إليها.
- تُخزَّن في `transitions.note`.

### 4. تعليقات على موضع في المخرج

المراجع يقول: «الكلمة الثالثة في السطر الثاني — تشكيلها خطأ». اليوم:
كتلة نصّ مفصولة عن المخرج. المطلوب: **تعليق مربوط بإحداثيات في الرندر**.

النموذج المبدئي:
```jsonc
{
  "type": "annotation",
  "target": {
    "kind": "text",
    "layer": "headline",       // مرجع طبقة القالب
    "wordIndex": 3,            // أو "range": [charStart, charEnd]
    "line": 2
  },
  "author_id": "…",
  "note": "التشكيل خطأ — يجب أن تكون مضمومة لا مفتوحة",
  "resolved": false
}
```

- المعاينة تعرض دبابيس (pins) في مواضع التعليقات.
- الفلترة: «التعليقات المفتوحة» / «تعليقاتي» / «تعليقات فلان».
- التعليق يُغلَق يدوياً — لا تلقائياً على أي تعديل (المعدِّل قد لا
  يكون يعالج التعليق).

**الخطر المؤجَّل:** ربط التعليق بإحداثيات pixel هشّ — تغيير fs يغيّر
الموضع. الحل: **ربط بمرجع منطقي** (layer + wordIndex) لا بـx/y.

### 5. الإشعارات

بلا إشعار، سير العمل يتوقّف: العمل ينتظر شخصاً لا يعرف أنه ينتظره.

- «عُيّن إليك مشروع» — عند دخول مرحلة يُطلب فيها دور المستخدم.
- «رُدّ عملك» — عند تحوّل عكسي على مشروعه.
- «تعليق جديد على عملك» — عند إضافة annotation على كيان الشخص.

القنوات (تدرّج):
1. **داخل المنتج** (bell icon + قائمة) — اليوم الأول.
2. **بريد إلكتروني** — الأسبوع الأول.
3. **Slack/WhatsApp webhook** — المرحلة 4.5 لاحقاً، ليس شرطاً للإطلاق.

### 6. سجل السير

يجاور سجل المراجعات لكن يركّز على **الحالة والتوقيت**:

```sql
CREATE TABLE project_state (
  project_id   uuid PRIMARY KEY REFERENCES projects(id),
  current_state text NOT NULL,          -- مرجع workflow.states[].id
  assignee_id  uuid REFERENCES users(id),
  since        timestamptz NOT NULL,
  tenant_id    uuid NOT NULL REFERENCES tenants(id)
);

CREATE TABLE workflow_transitions (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id   uuid NOT NULL REFERENCES projects(id),
  from_state   text NOT NULL,
  to_state     text NOT NULL,
  actor_id     uuid NOT NULL REFERENCES users(id),
  note         text,                    -- إلزامي على التحوّل العكسي
  created_at   timestamptz NOT NULL DEFAULT now(),
  tenant_id    uuid NOT NULL REFERENCES tenants(id)
);

CREATE INDEX ON workflow_transitions (project_id, created_at);
```

**تقارير مفيدة تنشأ منه بلا كود إضافي:**
- «كم يقضي كل مشروع في كل مرحلة؟» — كشف الاختناق.
- «من يردّ أكثر شيء ولمن؟» — دلالة تناسق تحريري.
- «متوسّط الوقت من مسودة إلى منشور» — KPI رئيسي.

## سياسة النشر (Terminal state)

`terminal: true` = لا انتقال بعده (مثل `published`). أثر:
- المشروع في حالة terminal **لا يُحرَّر** — يجب استنساخه (`clone`) أولاً.
- الاستنساخ يبدأ من `initial` state ويحمل `parent_project_id`.
- في السجل: «نسخة من مشروع X المنشور».

## عزل RLS

مطلق مثل `docs/14`. `tenant_id` على كل جدول، policy على كل `SELECT`
و `INSERT` و `UPDATE`.

## الأثر على المرحلة 4

**بندان جديدان في PHASES.md §المرحلة 4:**

- **سير العمل التحريري** — الجداول (`project_state` + `workflow_transitions`)
  + إعدادات المستأجر (workflow states/transitions) + الأدوار الموسَّعة
  + نظام الإشعارات (بريد + داخل المنتج) + قوالب سير عمل جاهزة.
- **التعليقات على موضع في المخرج** — نموذج `annotations` مربوط بمرجع
  منطقي (layer + wordIndex) لا بـpixel.

## ملاحظة تموضعية (يُنعكس في docs/01-product.md)

هذا يغيّر تصنيف المنتج من **أداة إنتاج فردي** إلى **نظام إدارة إنتاج
لفريق تحريري**.

**الأثر التسويقي:**
- يبرّر تسعيراً أعلى (باقة Agency فوق الباقة الفردية).
- يزيد الالتصاق — الفريق الذي يدير عمله في المنصة لا ينتقل بسهولة
  (بيانات السير موجودة هنا، لا في Trello المستنسخ).
- **لا يملكه أيّ منافس مباشر** — مسح docs/12 راجَع Placid و Bannerbear
  و Creatomate: أدوات فردية أو API بلا سير عمل تحريري. الميزة
  التنافسية ليست في الرندر بل في **إدارة الرندر جماعياً**.
